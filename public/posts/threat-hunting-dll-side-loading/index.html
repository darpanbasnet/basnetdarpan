Threat Hunting DLL Side-Loading from Social Lures

May 27, 2026 Darpan Basnet

DLL side-loading is effective because it abuses trust. A signed or legitimate executable runs, Windows searches for a dependency, and the attacker places a malicious DLL where the executable will load it. To an analyst, the first process may look normal. The behavior around it is where the hunt gets interesting.

Social lures make this technique more realistic. A fake recruiter message, a shared archive, or a “portfolio review” file can convince a user to extract and run something from a writable directory. The payload does not need to look like malware at first glance if the execution chain leans on a trusted application.

Hunt Hypothesis

The hypothesis I would test is:

A user executes a legitimate binary from a user-writable directory, and that binary loads a DLL from the same suspicious directory or from another non-standard path.

This is a stronger starting point than looking for one malicious filename. It focuses on behavior:

  • Legitimate executable in an unusual path.
  • DLL loaded from a user profile, downloads folder, temp folder, or extracted archive.
  • Parent process tied to user interaction, such as Explorer, a browser, Teams, Outlook, or an archive utility.
  • Network activity shortly after execution.
  • File creation events close to the execution time.

Data Sources

For Windows hosts, I want:

  • Process creation logs.
  • Sysmon image load events.
  • File creation events.
  • Network connection events.
  • Archive extraction or browser download evidence when available.
  • EDR process tree and reputation data.

Sysmon Event ID 7 can be noisy, but in a lab it is useful for building the analytic. In production, I would scope the rule carefully to suspicious directories, rare process names, or known side-loading candidates.

Useful Questions

During triage, I would ask:

  • Did the executable run from Downloads, Desktop, AppData, Temp, or an extracted archive?
  • Did the process load DLLs from the same directory?
  • Is the executable signed, and does the path match the expected vendor installation path?
  • What parent process launched it?
  • Did it make network connections after loading the DLL?
  • Was the same file seen on other hosts?
  • Did the user receive a related email, chat message, or browser download?

These questions help separate normal software behavior from a suspicious execution chain.

Example Detection Logic

A first-pass hunt query can look for signed executables running outside expected locations and loading DLLs from user-writable paths. The exact query depends on the telemetry schema, but the logic is:

process.executable in user-writable path
AND loaded_module.path in user-writable path
AND process.parent.name in common user-facing launchers
AND process.code_signature.trusted == true

That is not enough for a high-confidence alert by itself, but it is a strong hunt lens. Add rarity, network activity, or suspicious filenames to increase confidence.

Lab Simulation

In a lab, I would simulate the pattern with a known vulnerable or test-safe binary, a harmless DLL, and an extracted folder under a user profile. The goal is not to run real malware. The goal is to validate whether telemetry captures:

  • The original file write.
  • The executable launch.
  • The DLL load.
  • The parent-child relationship.
  • Any network activity.

If one of those pieces is missing, the detection may fail in production.

Response Notes

If the hunt returns a likely hit, preserve the folder contents, collect the process tree, hash the executable and DLL, and check for persistence. Side-loading is often a staging technique, so the next behaviors may include credential access, discovery, scheduled tasks, registry run keys, or outbound beaconing.

The important lesson is that trusted binaries do not guarantee trusted behavior. Context is the detection.
