Prioritizing Vulnerabilities with CVSS, EPSS, SSVC, and CKEV

May 24, 2026 Darpan Basnet

Vulnerability management becomes messy when every scanner finding is treated like an emergency. CVSS is useful, but severity alone does not answer the operational question: what should be fixed first with limited time?

I prefer a layered model that combines several signals:

  • CVSS for technical severity.
  • EPSS for exploit likelihood.
  • SSVC for decision-making context.
  • CISA KEV or known exploited lists for real-world exploitation evidence.
  • Asset criticality for local business impact.

The point is not to create a perfect score. The point is to make the decision defensible.

CVSS: Severity, Not Priority

CVSS describes technical characteristics: attack complexity, privileges required, user interaction, impact, and related factors. A high CVSS score matters, but it does not automatically mean a finding is the top priority.

A critical vulnerability on an isolated lab asset may be less urgent than a lower-scored vulnerability on an internet-facing identity system. CVSS gives the baseline. Context decides the queue.

EPSS: Exploit Probability

EPSS helps estimate the likelihood that a vulnerability will be exploited in the wild. This is valuable because attackers do not exploit every critical CVE equally. If EPSS is high and the asset is exposed, I treat the finding differently than a theoretical issue with little observed interest.

EPSS should not be used alone. It is a probability signal, not a guarantee.

SSVC: Decision Support

SSVC is useful because it pushes the conversation toward action. Instead of asking “how bad is this CVE?” it asks what decision should be made based on exploitation, exposure, technical impact, and mission impact.

That framing is helpful for teams because the output can become:

  • Defer.
  • Track.
  • Schedule.
  • Act immediately.

This maps better to real workflows than a long spreadsheet sorted only by scanner severity.

Known Exploited Vulnerabilities

If a vulnerability appears in a known exploited catalog, I treat it as a major priority signal. Active exploitation changes the risk conversation. Even if a local asset seems lower value, attackers often chain weaknesses and move laterally.

Known exploitation should trigger a check for:

  • Exposure.
  • Patch status.
  • Compensating controls.
  • Detection coverage.
  • Evidence of prior compromise.

A Practical Scoring Model

A simple model can be:

priority = severity + exploit_likelihood + exposure + asset_criticality + known_exploitation

Each component can be normalized into a small range, such as 0 to 5. The score is less important than consistency. If two analysts evaluate similar assets, they should reach similar conclusions.

What I Would Track

For each vulnerability, I want these fields:

  • CVE and affected product.
  • CVSS base score.
  • EPSS percentile or probability.
  • Known exploitation status.
  • Internet exposure.
  • Asset owner.
  • Business function.
  • Existing detections or compensating controls.
  • Remediation deadline.
  • Exception reason if not remediated.

This gives leadership a clear view and gives analysts enough context to avoid blindly chasing scanner output.

Detection Tie-In

Vulnerability management and detection engineering should reinforce each other. If a high-priority vulnerability cannot be patched immediately, write or validate detections for exploitation attempts. If exploitation is known in the wild, hunt for historical indicators and suspicious behavior around affected assets.

Prioritization is strongest when it produces action: patch, mitigate, detect, hunt, or accept with a documented reason.
