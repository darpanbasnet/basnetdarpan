Building a Threat Hunting Lab with Elastic Stack

May 29, 2026 Darpan Basnet

A detection lab should answer one question quickly: can I observe the behavior I care about, and can I turn that observation into a useful analytic? The lab does not need to be large, but it does need to be repeatable. I like Elastic for this kind of work because it gives me ingestion, search, dashboards, and detection rules in one place without hiding the raw event details.

Lab Goals

The first goal is telemetry coverage. A lab that only collects one type of event will teach you one type of detection. For Windows-focused hunting, I want at minimum:

  • Windows event logs for logon, process creation, service creation, scheduled tasks, and PowerShell activity.
  • Sysmon with a tuned configuration so process ancestry, network connections, image loads, and file events are easier to reason about.
  • Defender or other endpoint alerts when available, because detections should be compared against what the endpoint already knows.
  • DNS and proxy-style visibility if the lab includes outbound command-and-control simulation.
  • Authentication logs from cloud or identity systems when the hunt includes identity abuse.

The second goal is attack replay. If I cannot rerun the behavior, I cannot confidently tune the rule. Atomic Red Team, Caldera, custom PowerShell, and small Python scripts are useful here because they let me generate known behaviors and compare the expected event trail against what Elastic actually received.

Basic Architecture

My preferred small lab layout is simple:

  • One Elastic node for Elasticsearch and Kibana.
  • One Windows workstation target.
  • One Windows server or domain controller if testing domain behaviors.
  • One Linux host for attacker tooling, packet capture, and automation.
  • Elastic Agent or Beats on endpoints depending on what I am testing.

This is enough to test many useful detections: suspicious PowerShell, credential access attempts, persistence, lateral movement, unusual service creation, and suspicious network egress.

Ingestion Priorities

Start with endpoint data before adding complexity. Process creation is the backbone of most endpoint hunts because it links user context, parent process, command line, executable path, and timing. After process creation, add PowerShell logs, Sysmon image load events, and authentication events.

For PowerShell, I care about these data points:

  • Script block content.
  • Module logging.
  • Process ancestry.
  • User and host context.
  • Encoded command usage.
  • Network activity close to execution time.

For DLL side-loading and suspicious binary execution, Sysmon image load telemetry becomes important. It is noisy, so I usually test it in the lab first and then decide which paths, vendors, and process names deserve attention.

Detection Workflow

The workflow I use is:

  1. Pick a technique or behavior.
  2. Generate it in the lab.
  3. Confirm raw telemetry is present.
  4. Write a first-pass query.
  5. Add context fields that help triage.
  6. Test benign lookalikes.
  7. Promote the query into a detection rule only after I understand the failure modes.

For example, suspicious PowerShell should not be detected only by the string EncodedCommand. That catches some behavior, but it misses plenty and creates weak triage. A better analytic combines encoded commands, process ancestry, unusual child processes, downloaded content, suspicious flags, and the user or host role.

Dashboards That Actually Help

Dashboards should help answer triage questions, not just look busy. The most useful panels in my lab are:

  • Top parent-child process pairs.
  • Rare process execution by host.
  • PowerShell executions with command-line previews.
  • New services and scheduled tasks.
  • Outbound connections grouped by process.
  • Authentication failures and successes by account.

When I am testing a detection, I want the dashboard to show the surrounding story: what launched, what user ran it, what network connection followed, and whether the same pattern happened elsewhere.

What Makes the Lab Useful

The lab becomes valuable when it produces repeatable evidence. Every detection should have:

  • A short description of the behavior.
  • Required data sources.
  • A known test procedure.
  • Example matching events.
  • Known false positives.
  • Triage notes.

That turns the lab into more than a playground. It becomes a place to build detection knowledge that can move into production with fewer surprises.
